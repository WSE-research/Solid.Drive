= restoreTrashedFile

Reverses a soft delete: reads the tombstone, copies the payload, `index.ttl`, and (best-effort) the ACL back to the original location, restores the catalog row, then removes the trash copy.

== Sequence

Reads the tombstone first. If it's missing, nothing is written and the result is `{ ok: false, reason: 'missing-tombstone' }`. Then checks the original location isn't already occupied, via a `HEAD` on `index.ttl` rather than the container (pods keep empty containers around, so a container `HEAD` would false-positive).

If it's occupied and no resolution was given, nothing is written; the result names both versions being compared (whichever is currently there, and the one in the Recycle Bin) so a caller can ask the person which to keep. Given a resolution instead: moving the current one to the Recycle Bin first and then restoring into the now-free spot, or restoring alongside it under the same naming Dropbox uses for a kept duplicate: "(restored)", then "(restored 2)", "(restored 3)", and so on until a free spot turns up.

Once the location is settled, it ensures the target container exists, copies the payload back under its original filename (from the tombstone) and a fresh `index.ttl`, and restores the ACL snapshot if the tombstone says one was captured. ACL restore is best-effort: a failure there still returns success, just with `aclRestored: false`.

The catalog row is appended using the catalog and instance URIs stored on the tombstone, never recomputed, so it lands exactly where it was removed from. The trash copy is then removed via the same `deleteResource` used elsewhere; that's also best-effort, since a stale trash row is harmless once the restore itself has succeeded. Finally, `useCatalogVersion` and `useAclVersion` are notified for the original location.

Any failure while writing to the original location rolls back what was written and returns `{ ok: false, reason: 'failed', detail }`, leaving the trash copy untouched so the user can retry. If that failure comes after a "replace" already moved the file that was in the way, that move isn't undone; the result carries `occupantMovedToTrash: true` so a caller can say so, since the file is safe in the Recycle Bin but not where the person last saw it.

== Reuse

No new delete, catalog, or ACL-restore logic here: `appendToCatalog`, `deleteResource`, and `restoreAclFromSnapshot` are all reused unmodified. Replacing a conflicting file reuses `softDeleteFile` too, so it ends up in the Recycle Bin exactly the way any other delete would.

Permanent delete from trash isn't a service of its own, on purpose: `useTrashEntries` and `TrashView` just call `deleteResource({ containerUri: trashItemContainerUri, catalogUri: trashCatalogUri, metadataUri, fetch })` directly.
