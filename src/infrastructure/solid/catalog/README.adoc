= catalog

DCAT catalog operations for Solid Pods. All communication goes through raw `fetch`; LDO is not used.

The mutating functions (`appendToCatalog`, `appendFolderToCatalog`, `ensureCatalogRootEntry`, `removeFromCatalog`) read the whole Turtle document, apply the change to an in-memory N3 store, and PUT it back, rather than SPARQL PATCH, since PATCH support is inconsistent across Solid servers. A 404 GET starts from an empty store, so the same round trip creates the catalog on first write. `linkCatalogToProfile` is the exception: it stays a single-triple SPARQL PATCH, since the profile document is shared with other apps and a full rewrite is a bigger blast radius than one triple justifies.

A malformed existing document (leftover from an earlier bad write) gets truncated back to before the first syntax error and re-parsed, the same recovery `parseCatalogRecovering` uses for reads; a write then proceeds against that recovered prefix, which is what heals the document over time. Only a document with nothing recoverable makes the mutating functions throw, instead of risking an overwrite with an empty catalog.

Every mutating function is also queued per `catalogUri`: a plain GET/PUT has no server-side precondition, so two overlapping writes to the same document would otherwise silently discard one. See `catalogWriteQueues`'s comment in catalog.ts for the full reasoning.

Every entry also carries a unique tag, minted automatically unless a caller supplies one it already has from elsewhere. A supplied tag is checked against the catalog's tombstone log, and the add is skipped if that tag was already tombstoned. Removing an entry tombstones its tag, and does so as part of the same queued write, so a same-catalog add checking that tag concurrently can't slip through with a stale answer. This is the piece a second client needs to avoid resurrecting a file it deleted here: nothing in this app re-adds an entry with a tag of its own yet, since nothing here keeps an offline copy to resupply one from. See link:../catalogTombstones/[catalogTombstones] and link:../entryTag/[entryTag].

== Exports

[cols="1,3", options="header"]
|===
| Name | Description

| `resolveCatalogUri(profile, storageRoot)` | Returns `profile.catalog["@id"]` or falls back to `{storageRoot}catalog.ttl`
| `appendToCatalog(params)` | Adds a file's dataset and distribution entry. Types it as `dcat:Dataset` and `sd:File`, writes `sd:hasParent` when `parentUri` is set, and assigns `sd:tag`. Returns `{ suppressed }`, true when a given `tag` was already tombstoned and nothing was written
| `appendFolderToCatalog(params)` | Adds a folder's dataset entry (no distribution). Types it as `dcat:Dataset` and `sd:Folder`, writes `sd:hasParent` when `parentUri` is set (omitted for a folder with nothing above it, e.g. a trash item), and assigns `sd:tag`. Same `{ suppressed }` result as `appendToCatalog`
| `ensureCatalogRootEntry(params)` | Registers the pod's storage root as its own parentless entry, the terminator every folder path walk reaches. Safe to call repeatedly; duplicate triples are no-ops
| `isFolderEntry(entry)` | True when a `CatalogEntry` is a folder, whether marked with the current `sd:Folder` class or the legacy `ldp:Container` marker
| `FOLDER_CLASS_URI` | The `sd:Folder` class/`conformsTo` value marking a folder
| `FILE_CLASS_URI` | The `sd:File` value files are typed with. Descriptive only, nothing routes on it
| `LEGACY_FOLDER_CLASS_URI` | The `ldp:Container` marker folders were written with before `sd:Folder` existed; `isFolderEntry` still recognizes it
| `removeFromCatalog(...)` | Removes a dataset entry and tombstones its `sd:tag`, if it had one; no-ops if the catalog isn't reachable (`HEAD` check first)
| `parseCatalog(turtleText, baseUri?)` | Parses Turtle into `CatalogEntry[]`, including each entry's `parentUri` from `sd:hasParent`. Malformed Turtle comes back as `[]`, the same as a genuinely empty catalog
| `parseCatalogRecovering(turtleText, baseUri)` | Same as `parseCatalog`, but salvages what it can from malformed Turtle and returns the parse error alongside the recovered entries, instead of discarding it. `useCatalog` uses this so a corrupt catalog still shows what could be read
| `linkCatalogToProfile(catalogUri, webId, fetch)` | Adds a `dcat:catalog` triple to the user's profile document via SPARQL PATCH
| `resourceFileName(uri)` | Decodes a URI's resource filename, falling back to the raw tail on malformed percent-escapes
| `buildEmptyCatalogTurtle(catalogUri)` | Turtle template for a new, empty catalog with an explicit `@base`. Used directly by `useAccessRequests`, independent of `appendToCatalog`'s own 404 handling
|===

The vocabulary (`sd:StorageObject`, `sd:Folder`, `sd:File`, `sd:hasParent`, `sd:deletedAt`, `sd:tag`) is defined in `public/vocab/solid-drive-catalog.ttl`, published under the `https://purl.org/solid-drive/catalog#` PURL. `sd:deletedAt` is defined there but not yet written by this module.

`appendToCatalog`/`removeFromCatalog`/`parseCatalog` are parameterised entirely by `catalogUri`, so `softDeleteFile` and `useTrashEntries` reuse them unmodified against `trash/catalog.ttl` instead of the main catalog; see link:../trashPaths/[trashPaths].
