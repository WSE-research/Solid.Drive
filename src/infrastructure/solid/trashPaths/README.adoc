= trashPaths

URI scheme for the trash container and its per-item resources: `trash/catalog.ttl` at the pod storage root, and `trash/<id>/` per soft-deleted item holding a fixed-name `payload`, `index.ttl`, `acl-snapshot.ttl`, and `tombstone.ttl`. The trash lives at the storage root rather than under the app container, so it's a pod-wide recycle bin rather than scoped to this one app.

The payload keeps its original filename only at its active location. Inside the trash it's always named `payload`, regardless of the source file's name or extension. This sidesteps filename edge cases (spaces, accents, percent-encoding) for a copy that's purely internal bookkeeping; the original name lives on the tombstone (`originalBinaryName`) and is restored verbatim on undelete. Trash item ids are plain unique strings (e.g. `crypto.randomUUID()`) supplied by the caller, so this module has no side effects and stays fully deterministic in tests.

The container name is deliberately `trash/`, not `.trash/`: a leading dot reads as "hidden" to most generic Solid pod browsers and gets filtered out of their listing by default, making the trash hard to inspect outside this app. It's a real, plainly-named, fully addressable container. Hiding it from end users in *this* app's regular My Files view is done at the application level instead (`isVisibleContainer` in link:../../../features/file-explorer/services/fileFilter/[fileFilter]), not by relying on a naming convention. Search stays clean without any extra filtering because trashed items live in a separate trash catalog (`getTrashCatalogUri`) that `useFileSearch` never reads from.
