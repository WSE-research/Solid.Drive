= Bulk upload: race conditions and transfer concurrency
:toc: macro
:toclevels: 3

Analysis and measurements behind making the bulk upload queue concurrent.

toc::[]

== Summary

The bulk upload tray processed one file at a time. The serialisation was deliberate — the comment read _"processing items one at a time so the catalog SPARQL PATCH never races on the same container"_ — but it was far broader than the hazard it was protecting against, and it was hiding three further races of its own.

Per file, an upload makes four network round trips:

[cols="1,4,2"]
|===
| # | Step | Shared state?

| 1 | create the per-file container | *partly* — LDO implements `createChildAndOverwrite` as `DELETE` on the target plus `POST` to the **parent** container, so this writes the shared destination
| 2 | upload the binary | no — same `DELETE` + `POST` shape, but against the per-file container
| 3 | write `index.ttl` | no
| 4 | `PATCH <catalog>` — append the DCAT entry | *yes*
|===

NOTE: The real request shape is at least six round trips, not four: LDO's
`createChildAndOverwrite` and `uploadChildAndOverwrite` each issue a `DELETE`
followed by a `POST` to the parent, rather than a single `PUT` to the child.
The benchmark below models the simplified four-`PUT` shape, which understates
both the absolute cost and the benefit of concurrency — see _Threats to
validity_.

Only step 4 touches state shared with other uploads. Steps 1–3 are scoped to the file's own subtree and parallelise cleanly. So the fix is to bound-and-parallelise the transfer and serialise *only* the catalog write, rather than serialising everything because one part needs it.

Measured against a real Community Solid Server: *2.86× faster* at the new default of four concurrent transfers, under a realistic 40 ms round-trip.

== Race conditions found

=== R1 — Concurrent catalog bootstrap loses entries (would have been introduced by naive concurrency)

`appendToCatalog` bootstraps a missing catalog:

[source]
----
PATCH <catalog>  ->  404
PUT   <catalog>  <-  empty catalog
PATCH <catalog>  ->  retry
----

Run two of those at once against a fresh Pod and both see the 404, both `PUT` the empty catalog, and *the later `PUT` erases the entry the earlier `PATCH` just wrote*. The entry is gone but the file is on the Pod, so it is invisible in the UI and never cleaned up.

This is the hazard the original serialisation was protecting against, and it is real. It is preserved: `upload` now takes a `withCatalogLock` wrapper, and the queue passes a mutex. The critical section covers the append, the rollback and the profile link — releasing early would let the next upload observe a half-written catalog.

Note the append itself is `INSERT DATA`, which is commutative at the RDF level; it is the bootstrap that is not.

=== R2 — In-batch duplicate detection was blind, and the collision key was wrong

The duplicate check compared against `catalogEntries`, a prop that only refreshes after a server round trip. Within one batch it is therefore *always at least one upload stale*: drop two files with the same name in one drag and the second passes the check.

Worse, the check compared *file names* while the actual collision is on the *container slug*. `containerSlugFor` lower-cases and collapses every run of `[^a-z0-9.]` to a single `-`, so `"a b.txt"` and `"a-b.txt"` both become `a-b.txt` — and the container is created with `createChildAndOverwrite`. Two such files silently overwrite each other, with two catalog entries pointing at one binary.

This bug predates the concurrency work; serialising did not help, because the staleness is in the data, not the timing.

Fixed by tracking claimed slugs in the tray for the lifetime of the batch, keyed by destination so the same name in two folders is still fine. A failed item releases its slug so a retry can proceed. `containerSlugFor` moved into its own module so the writer and the de-duplicator share one rule and cannot drift.

=== R3 — Items enqueued or retried during a drain could be stranded forever

The drain kept a `handledIds` set for its lifetime and found work with `itemsRef.current.find(...)`, where `itemsRef` is assigned during render. Between items it did:

[source,typescript]
----
// Allow setItems to flush so itemsRef.current reflects latest snapshot.
await Promise.resolve();
----

A microtask yield does not guarantee React has committed, so the snapshot could be stale. And `retry` only flipped an item's status back to `queued`; if its id was already in `handledIds`, the running drain skipped it. The drain then ended without re-checking, and the restart came from a `useEffect` on `items` — which does not re-fire, because `items` did not change after the drain exited. The row sat in `queued` indefinitely.

Same for files enqueued mid-drain: the effect fired, `processQueue` returned early on `isProcessingRef`, and nothing rescheduled them.

Fixed structurally rather than patched: the authoritative model is a `Map` in a ref, mirrored into React state purely for rendering, and scheduling is a `pump()` that anything can call. An item is claimed synchronously, before any `await`, so two pumps in one tick cannot double-start it. This removes the class of bug rather than the instance.

=== R4 — State updates after unmount

`updateItem` was called on several paths without checking `cancelledRef`. Now every publish goes through one function that checks it once.

== The concurrency model

[source]
----
                       ┌─ transfer pool (ENV.uploadConcurrency, default 4) ─┐
enqueue ──> pump() ──> │  container PUT ─> binary PUT ─> index.ttl PUT      │
                       │                                        │           │
                       └────────────────────────────────────────┼───────────┘
                                                                v
                                                      ┌─ mutex (size 1) ─┐
                                                      │  catalog PATCH   │
                                                      └──────────────────┘
----

Both are the same primitive: `createMutex()` is `createTransferPool(1)`.

The pool bound matters even though browsers already cap connections per origin. That cap queues invisibly at the network layer — after the app has committed memory for every in-flight `File` body and after the Solid client has minted a DPoP proof for each one. Bounding in the application keeps the queue observable, keeps memory proportional to the pool rather than the batch, and gives one knob to tune.

That knob is `VITE_UPLOAD_CONCURRENCY`, which is what `SolidPodServerPerformanceAnalysis` varies as the "number of Solid.Drive threads".

== Measurements

`scripts/benchmark-upload-concurrency.mjs`. It reproduces the four-step upload shape against a live Community Solid Server over real Solid-OIDC/DPoP, and sweeps the pool size. It does not drive the React hook: shape validation and LDO bookkeeping are CPU-bound and identical at every concurrency, so including them would only dilute the effect being measured.

Workload: 24 files × 64 KiB, 3 repeats per level, median reported. Server: Community Solid Server 7.1.0 in Docker, file backend, WebACL, on the same host.

=== Reading the numbers

*Loopback understates the win, and that is expected.* The Solid performance literature is emphatic that removing per-request latency is precisely what makes request count stop predicting wall-clock time — several studies find no correlation, and all of them ran on localhost or a simulated network. The real quantity is `requests × (RTT + TLS + DPoP + authorization)`. A Pod reached over the internet sits at the far end of that spectrum from loopback, so the 40 ms column is the more representative one for a deployed app, and even it is conservative for mobile.

*Four is the sweet spot, and the reason is the mutex.* Under latency, 4 is the optimum and 8 and 16 are slightly *worse*. Once the transfers overlap enough, the serialised catalog `PATCH` becomes the bottleneck, and adding pool slots only adds contention in front of it. This is a real ceiling, not measurement noise — the 16-way samples are the tightest in the table (1986–1992 ms).

*Consequence for future work:* the next meaningful gain is not a bigger pool, it is making the catalog write cheaper — batching one `INSERT DATA` per drain instead of per file would move the serialisation point from N round trips to one. That is a larger change to `appendToCatalog`'s contract and is deliberately not in this commit.

=== Threats to validity

* *The modelled request shape is simpler than the real one.* The script issues
  four `PUT`s per file; LDO issues at least six requests, two of them `POST`s to
  the shared parent container. Re-running with the real shape gives a *larger*
  speed-up (c=1 8230 ms, c=4 2256 ms = 3.65x, c=16 2113 ms = 3.89x) and moves
  the optimum to 16. The numbers below are therefore a lower bound on the
  benefit, and the default of 4 is conservative rather than optimal.
* *`notifyCatalogChanged` is not modelled.* It triggers a catalog refetch per
  file, which is shared network work, not the CPU-bound bookkeeping this
  document previously claimed.
* *The synthetic latency is applied once per request.* On a server that demands
  a DPoP nonce the retry would not be charged a second sleep, so RTT would be
  under-modelled. The CSS used here issues no nonce, so every request is exactly
  one round trip.
* *n=3, fixed sweep order.* Enough to separate the 1-vs-4 effect, not enough to
  separate 4 from 8.

=== Reproducing

[source,bash]
----
docker run -d --name css -p 3000:3000 solidproject/community-server:7.1.0 \
  -c @css:config/default.json -p 3000 -f /data \
  --baseUrl http://localhost:3000/

node scripts/benchmark-upload-concurrency.mjs \
  --base-url http://localhost:3000/ \
  --files 24 --size-kb 64 --levels 1,2,4,8,16 --repeats 3 [--latency-ms 40]
----

The published port must equal the internal port and the base URL must use it: CSS validates a DPoP-bound token by dereferencing the WebID *from inside the container*, so a mismatched port makes every authenticated request fail with a bare 401.

== Not done

* *Downloads are still serial.* The task named uploads and downloads; `downloadResource` is invoked per user action, one at a time, and has no batch path to parallelise yet. Adding one is a UI change, not a scheduling change.
* *Batched catalog writes* — see above; the measured ceiling makes this the highest-value next step.
* *Per-file progress* — the pool reports queued/active counts, but `uploadChildAndOverwrite` gives no byte progress, so rows remain binary (uploading → done).
